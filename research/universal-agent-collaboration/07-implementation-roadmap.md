# 07. Implementation roadmap

Every phase requires human review of the research before implementation. Complexity is relative to the existing controller and dependency surface. Fixture and live qualification have separate acceptance gates.

| Phase | Repositories and reuse | New boundary, compatibility and dependencies | Tests, security and acceptance | Estimate / confidence |
|---|---|---|---|---|
| 0. Choose the boundary | Software Factory, Dispatch, Kujo Agents. Reuse local control, pinned roles, handoffs, native state and observer | Review workspace grants and exact opt-in command types, publication policy, event v1 and native ownership. Confirm whether a per-mission staged assistance response plus new bounded invocation is sufficient for pilot. No native format change. | Approve threat model, fixture, replay semantics and out-of-scope list. Name owner of caller-to-submission reconciliation. | Small / high |
| 1. Local/custom proof | Software Factory. Reuse controller policy, fixed local control tool, worker/role contracts and Floor projections | Add a local opt-in collaboration boundary with configured principals, versioned event schema, bounded store and command inbox. Keep native arguments and outputs compatible. Store accepted intent keyed to its prepared ID before submission. Add typed, advisory handoff output or controller-derived assistance signal as an opt-in profile. | Offline two-agent role fixture, reviewer request and result, queued human start, restart and duplicate tests, unchanged native release gates and egress deny cases. Open a mission from the custom interface and observe linked evidence. | Medium / high |
| 2. Slack vertical and independent path | Software Factory, optionally reuse Chat SDK Slack transport or a direct connector guided by Leash. Use the same custom interface in Phase 1 | One bot identity, explicit scoped binds, thread updates, source occurrence dedupe, provider mapping, and allowed statuses. Connector can run outside controller; no durable schema fork. Slash/interaction/mentions only stage typed intents. Separate install approval. | Use signed fixture plus independent custom path first. After approval, deliver in one sandbox workspace, prove same agent IDs and payload shape in both interfaces and same thread correlation. Redelivery, revoke, 429, edit/delete, mirror loops and external approval denial. Require a second independent network before declaring provider portability. Use Matrix with a dedicated bot and bounded room. | Medium / high for custom, medium for live Slack/Matrix |
| 3. Reuse qualification | Software Factory and existing Kujo Paperclip plugin. Compare Board local/hosted, Paperclip issue/wakeup and Chat SDK Teams | Conformance spike for Board storage and sync ports, compare export/retention, isolation and uncertain sends. Paperclip host API maps issue → intent → native receipt and keeps Paperclip scheduling distinct. Teams adapter uses maintained SDK/JWT path and conversation references. Pin tested versions. | Board crash/reopen, external principal scopes, replay, opt-out and mirror dedupe. Paperclip checkout/run, revoked workspace and closed issue must not change native run. Teams endpoint verifies tenant and installation and handles proactive failures. No new collaboration authority. | Medium to large / medium |
| 4. Cross-factory and hosted | Product Launch and one independent factory, plus Software Factory. Reuse child evidence and shared profile/Ability contracts | Adopt envelope/projection, extract portable package only after independent use, enable request grants per factory. Review hosted tenant identity, object ACLs, service auth, concurrent event fanout, retention and disaster recovery. Add A2A or external adapter if justified. | Local cross-factory handoff with destination-owned gate, revocation, blocked source impersonation, drain/replay and export/import tests. Hosted isolation/restore/effect-only qualification before enabling general work. | Large / medium-low until adoption |

Prioritize Phases 0–2. To prove portability, run both surfaces against the same workspace bindings and same canonical IDs, including a cross-interface reply. For external-network portability, add Matrix as the next test because it can be separately hosted and does not share Slack APIs or identity. Do not route the two initial adapters through one provider's mirrored feeds. Keep Board and Paperclip task semantics optional. Avoid a common execution scheduler, general chat UI, separate approval ledger and new broker in the initial milestones.
